# 共用程式碼修改原則

取自 [Karpathy guidelines](https://github.com/multica-ai/andrej-karpathy-skills)。
這套原則偏向謹慎、犧牲速度；typo 這類小改動可自行判斷，不必走完整流程。

## 1. Think Before Coding
**不要假設、不要隱藏困惑、把取捨講出來。**
- 動手前先明確說出你的假設；不確定就問
- 需求有多種解讀時，列出來讓使用者選，不要自己默默挑一種
- 有更簡單的做法就提出來，必要時提出反對意見
- 有不清楚的地方就停下來，說明哪裡不清楚，然後發問

## 2. Simplicity First
**用最少的程式碼解決問題，不做推測性的設計。**
- 不加沒被要求的功能、單次使用的抽象層、可設定化
- 不為不可能發生的情境寫錯誤處理
- 如果 200 行能寫成 50 行，就重寫

## 3. Surgical Changes
**只改必要的地方，只清理自己造成的問題。**
- 不順手改善相鄰的程式碼、註解、格式；配合既有風格
- 發現無關的 dead code 只提出來，不要刪
- 只清掉「自己的改動」造成的未使用 import／變數
- 檢驗標準：每一行 diff 都要能追溯到需求

## 4. Goal-Driven Execution
**先定義成功標準，反覆執行直到驗證通過。**
- 把任務轉成可驗證的目標：
  - 「加驗證」→ 先寫無效輸入的測試，再讓測試通過
  - 「修 bug」→ 先寫能重現 bug 的測試，再讓測試通過
  - 「重構」→ 確認重構前後測試都通過
- 多步驟任務先列出簡短計畫，每一步都附上驗證方式：
  ```
  1. [步驟] → 驗證：[檢查方式]
  2. [步驟] → 驗證：[檢查方式]
  ```
- 宣稱完成之前，必須實際跑過驗證，並確認輸出結果
